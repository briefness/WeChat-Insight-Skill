# 我把一个公众号 Skill 从“规则很多”改到“路径清楚”

> **使用假设**：项目复盘；目标读者为使用 AI Skill 的开发者；核心目标为经验分享 + 互动；采用独立开发者调性。
>
> 本示例基于当前仓库的真实修改、Git 基线文件和本地校验结果。由于图片工具未参与本次优化，示例采用纯文字降级模式。

## 备选标题（3 个）

1. **推荐：我把一个公众号 Skill 从“规则很多”改到“路径清楚”**
2. 写 Skill 踩过最隐蔽的坑：同一条规则在不同文件里各说各话
3. 一个公众号写作 Skill 的真实重构：我是怎么排查并修掉跨文件规则冲突的

## 摘要

写作 Skill 规则越写越厚，输出反而容易跑偏。这次我从入口、reference、README 和示例里的真实冲突下手，复盘怎样划分职责、补齐降级分支，并跑通本地一致性校验。

## 正文

写完十几份规范文档后，我手头这个公众号写作 Skill 反而更不稳定了。

打开文件逐行排查，毛病比想象中更具体：**同一件事在不同文件里写了不同答案。** 模型先读到哪一段，输出就偏向哪一段。

这次重构只做一件事：让 Skill 在处理配图、封面、示例和发布时，沿着唯一明确的执行路径走，不再靠模型临场猜。

> 【配图建议：封面图；一摞互相交叉、带有冲突标记的规则卡片，在画面中央被整理成“入口”“写作”“图片”“发布”四个清晰文件夹；使用克制的编辑概念风格，不使用固定 IP；主视觉集中在中央 60% 安全区；2.35:1】

## 先定目标：让每条规则只归一个地方管

动手改 Skill 时很容易犯懒：看到入口文件太长，直接删字数压短。

单纯压短解决不了问题。入口变短了，只要 reference 里还留着互相打架的说法，模型照样会跑偏。真正要立住的规矩很简单：**每条规则只能有一个归属文件，每个分支都要写清触发条件。**

我最后按职责把仓库拆成四层：

- `SKILL.md` 只管触发条件、执行顺序、输出契约和硬红线，把标题、语气和图片细则全部移出去。
- `writing-playbook.md` 专管资料研究、标题、结构、调性和合规细则，不插手发布脚本的运行逻辑。
- 图片 reference 专管视觉系统、封面、插图和流程图，不改文章写作目标。
- `README.md` 面向使用者说明能力和边界，不承载内部执行细则。

判断一条规则该不该留在入口，可以过三道筛子：它决不决定“下一步做什么”？是不是每次触发都要读？会不会和下游 reference 重复？只要前两问答“否”，就直接移出入口。

## 再改结构：把厚入口收成路由器

旧版入口同时塞进了标题写法、语气模板、排版规范、配图细则和合规清单。内容看着全，每次触发却要一股脑全加载，既吃上下文，又容易互相覆盖。

删改时我只留下决定流程走向的骨架：输入判断、工作流、输出契约、文章类型路由和硬检查。其余细则全部沉淀到对应的 reference 里。

这样拆完，规则总量没丢，只是换了位置：入口告诉模型“这一步该去读哪份文件”，reference 告诉模型“具体怎么干”。

如果你也在整理越写越长的 Skill，可以按这个顺序动手：

1. 先圈出每条规则的核心动作：判断、生成、检查、发布、降级
2. 判断类和输出契约留在入口
3. 生成类细节挪进对应 reference
4. 检查类在入口只留硬门槛，细项交给 reference
5. 发布类只保留触发条件和失败处理入口

改完之后怎么验收？别数删了多少行，直接搜核心关键词，看同一个问题在仓库里还会不会冒出两个版本。

## 坑一：图片到底必须生成，还是可以留占位？

**触发场景：** 核对“可直接发布”输出契约时，我同时翻了旧版入口、插图 reference 和示例文章。

**看到的现象：** 旧版入口写着配图必须实际生成，禁止留占位符；插图 reference 允许写草稿时先留配图位；示例文章放着文字占位，发布前检查里却写着图片已自动生成。

说直白点，三个文件对“文章到底交付到哪一步”各说各话。问题出在执行分支没定义清楚。

**根本原因：** 图片规则被复制进了多个文件，却漏了一个前置能力判断：当前运行环境到底有没有图片工具？用户要的是完整图文还是纯文字稿？

**实际处理：** 把配图拆成两条清晰分支。环境有图片工具且用户未指定纯文字时，走完整图文模式，实际生成并嵌入图片；工具不可用、生成失败或用户只要纯文字时，走纯文字降级模式，输出包含图片类型、画面、标注和比例的配图建议，并在发布前检查里明确标出“图片尚未生成”。

**验证结果：** 入口、README、示例和三份图片 reference 全部统一了模式名称；全局扫描后，旧的“图片已生成”矛盾说法已经清零。

**怎么避免：** 同一个能力只要存在两种合法交付形态，就必须在入口定义分支和降级条件，不能留给下游 reference 各自发挥。

排查同类分支冲突，直接问四个问题：

- 当前环境有没有图片工具？（归入口的能力判断）
- 用户要完整图文还是纯文字？（归入口的模式判断）
- 这一段该配封面、流程图还是叙事图？（归图片 reference）
- 生成失败后降级还是中断？（由入口和对应 reference 共同约定）

> 【配图建议：分支决策图（B）；橘猫代表 Skill 执行器，在“图片工具？”菱形判断节点内手持开关拨向“完整图文”与“纯文字降级”两条分支，动作直接绑定决策节点，移除橘猫后条件分流的触发动作缺失；关键标注“图片工具？”“完整图文”“纯文字降级”；4:3】

## 坑二：橘猫有时是角色，有时成了角落贴纸

**触发场景：** 梳理完配图分支后，我继续核对视觉 IP 规范，想让同一只橘猫保持稳定的识别度。

**看到的现象：** 旧版入口写着流程图和封面不加橘猫；流程图 reference 又允许在部分节点旁放猫；封面模板则直接把橘猫当成了固定主视觉。

一刀切改成“所有图都加猫”照样行不通。流程图里多一只站在角落卖萌的猫，既挡信息又显廉价。

**根本原因：** 旧规则只按图片类型拍脑袋决定“加不加猫”，压根没定义橘猫在画面里承担什么信息角色。

**实际处理：** 给正文图加上硬门槛：生成前先回答橘猫代表谁、在执行什么动作、动作绑定哪个节点、删掉猫后图里缺了什么。答不出来就重构画面，禁止当背景贴纸或水印。封面则完全独立，按正文核心冲突动态生成，禁用橘猫和任何固定 IP。

**验证结果：** 叙事图、流程图和设计系统统一了同一套角色检查；封面彻底走内容驱动路线，不再捆绑固定吉祥物。

**怎么避免：** 视觉 IP 放进正文图，必须让它干活。一旦发现它只是站在旁边凑数，立刻改动作或重选配图位置。

## 最后验证：别把工具环境报错当成项目失败

> **注：** 以下四项针对的是本次 **Skill 仓库重构**的代码与文档一致性检查，不是公众号文章的通用发布前检查；文章自检见 `SKILL.md` 第 5 步。

全部改完后，我跑了四类本地校验：

1. `git diff --check`：排查空白字符和补丁格式问题
2. YAML 解析：确认 `SKILL.md` frontmatter 只包含 `name` 和 `description`
3. 相对链接扫描：验证 `SKILL.md`、README 和各 reference 里的本地链接全部指向真实文件
4. 旧规则关键词扫描：排查冲突配色、旧标题流程和装饰性橘猫指令残留

中途遇到一个小插曲：手头的 `quick_validate.py` 因为本机缺少 `PyYAML` 依赖直接报错退出。我没有把“脚本起不来”误判成“Skill 校验失败”，而是改用系统自带的 Ruby YAML 解析器跑完等价检查，同时在交付记录里注明这个环境限制。

校验工具报错，和被校验的项目本身出错，完全是两码事。排查时先分清这一层，能省下大量冤枉时间。

## 一份可以直接照抄的 Skill 体检清单

折腾完这一轮，我更确信一点：**Skill 稳不稳，看的是每条规则有没有唯一归属和可验证路径，和写得多长没多大关系。** 下次再维护大 Skill，我会先跑一遍冲突扫描，再决定删什么、补什么。

如果你也在维护一个越来越臃肿的 Skill，可以用这 6 条逐项过一遍：

- 入口文件是否只留路由、契约和硬红线，把生成细则放进 reference？
- 同一条核心规则在入口、reference、README 和示例里说法是否完全一致？
- 外部工具不可用时，有没有写死明确的降级形态？
- 示例文章展示的写法，是不是真的遵守了最新规则？
- 每个 reference 是否只负责单一主题，没有越权定义全局约束？
- 每条硬规则有没有对应的检查动作，而不是一句空泛提醒？

顺手问一句：你平时维护 Skill 或提示词时，最常碰到“多个文件互相打架”的是哪一块？输出格式、工具降级，还是风格示例？
